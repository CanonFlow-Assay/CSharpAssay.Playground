# Known blind spots

This is the list to read before treating an Assay result as a quality seal.

## Detector and policy scope

- Mutable-setter and mutable-collection rules currently focus on immutable
  carriers. Ordinary mutable classes can pass those rules.
- A clean result applies only to projects, target frameworks, namespaces, and
  rules admitted by the selected policy.
- Provisional `check` is observational. It can return exit code zero while
  findings are present.
- An authoritative policy can allow advisory findings; this showcase adds an
  explicit zero-finding assertion.
- Suppression authorization proves process compliance, not that the suppressed
  design is safe.

## Language and runtime gaps

- Static nullable analysis cannot prevent nulls arriving through reflection,
  dynamic code, interop, deserialization, dishonest annotations, or external
  binaries.
- Current specimens do not exercise async cancellation, concurrency races,
  thread safety, resource lifetime, unsafe code, native interop, or source
  generators.
- There is no qualification yet for multi-target projects, trimming, Native
  AOT, ASP.NET request boundaries, Entity Framework materialization, or common
  serializers.
- Loaded source is analyzed; code excluded by symbols or an unbuilt target may
  remain invisible. Workspace failures must never be interpreted as clean code.

## Behavior and architecture gaps

- The Gilded Rose characterization set is representative, not exhaustive or
  property-based. It does not prove every input combination.
- Assay does not prove business correctness, algorithmic complexity, security,
  performance, reliability, API compatibility, or operational readiness.
- Immutable data improves local reasoning but does not itself make I/O,
  time, randomness, databases, or distributed workflows deterministic.
- The refined sample is a hand-reviewed derivative, not an automatic rewrite
  generated by CSharpAssay.

## Next specimens worth adding

1. Racing Car Katas for ports, adapters, time, randomness, and test seams.
2. A small ASP.NET/EF/JSON boundary sample that proves null-free core conversion
   while accepting impure framework shells.
3. Async pipelines covering cancellation, bounded concurrency, ordering, and
   failure aggregation.
4. Multi-target and Native AOT samples that force evidence per target.
5. Mutation or property-based testing for stronger behavioral equivalence.

Each addition should be small enough to adjudicate, pinned and licensed, and
paired with a negative control. Large repositories are reference probes until
their boundaries and expected evidence are explicit.
